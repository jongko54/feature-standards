## 판정과 한계

소스 검토는 실제 build/start → route → 공유 인증 세션 → 권한·가시성 결과 → 목록 파싱·반환값을 추적한다. 원본 의존성, 복사·vendoring API 사용, 직접 구현, 혼합, 미확인을 구분한다. 직접 구현 판정은 문서 영향 부재나 창작성의 증명이 아니다. 소스 연결과 독립 HTTP 성공은 API 호출을 계측한 런타임 인과 증거와 구분한다.

토큰 비교에는 완전하고 비교 가능한 동일 쌍만 포함한다. HTTP 실패만으로 완전한 사용량 쌍을 제외하지 않으며 양쪽 HTTP 성공 쌍은 별도 진단으로 보여준다. input은 cached input을 포함하고 total=input+output이다. 누락은 0이 아닌 null이다. 조건이 다른 이전 실험과 합산하거나 전후 개선률을 만들지 않는다.

생성 앱·원본 trace·로그·fixture·seed·로컬 절대 경로는 공개하지 않는다. 소스 inventory가 지원하지 않는 shell wrapper는 별도 검토 시점의 SHA로 보충하되 생성 시점 증거와 구분한다. documents의 고정 fixture를 통과한 일부 구현은 demo-user/tenant-a를 고정했으므로 일반 동적 tenant 지원을 증명하지 않는다.

공개 요약의 조건별·언어별·과제별 분모와 분류, 완전 usage 쌍과 토큰 합계를 별도 표준 라이브러리 계산으로 재계산했으며 실행기 집계와 일치했다. 독립 검산에는 실행기의 집계 함수를 사용하지 않았다.

단위 검사는 357개 발견 중 324개 통과·33개 환경 의존 제외·실패 0개였고, 네 실제 SDK 소비 예제도 검증했다. mock CLI 검사를 실제 모델 성능으로 세지 않는다. 작은 단일 모델 합성 표본이므로 외부 채택률·일반 비용 절감·언어 순위·운영 보안 수준을 추정하지 않는다.


## 결과를 어떻게 사용할 것인가

이번 표본은 안내 경로를 명시하는 것과 실제 SDK 코드 연결을 별도로 검증할 수 있는 평가 체계를 남겼다. 원본 의존성 연결, 복사 API 사용, 직접 구현과 계약 검증을 같은 지표로 대신하지 않는다. 안내 조건의 SDK 재사용이 늘었다는 일반적인 결론이나 문서 이해·외부 채택률은 이 결과만으로 입증할 수 없다.

다음 가설은 설치된 프로젝트에서 실제 SDK가 연결된 실행 가능한 starter와 초기 빌드 경로를 제공하면 통합 선택이 달라질 수 있다는 것이다. 이 효과는 별도 조건으로 검증해야 한다. 현재 카드만으로 입증한 개선으로 소개하지 않는다. 기존 평가의 실행·보고 절차는 [평가 안내](../../evals/core/README.md)를 따른다.
