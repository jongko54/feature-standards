# 성능 검증 과제

작성일: 2026-11-21. 상태: **계획만 작성, 아래 과제 모두 미실행**.

이번 변경은 검증 과제와 문서 연결만 추가한다. 부하 도구 구현·설치, API 부하,
실제 모델 호출, 성능 개선, 패키지 게시와 운영 배포는 실행하지 않는다.
아래 명령과 예상 산출물은 이후 착수할 작업이며 통과 기록이 아니다.

## 목표와 현재 근거

Python·Go·Java·Rust의 인증·권한·목록 구현이 어떤 조건에서 얼마나 처리하는지,
설치한 CLI와 SDK 안내가 AI 개발의 성공률·시간·토큰에 어떤 영향을 주는지 측정한다.
서버 처리량, CLI 실행 시간, AI 개발 효율은 서로 다른 결과로 보고한다.

- 작성 전 기준 소스: `1f078c17618e19e9fe9ebf1e9fd4910fea3dcee1`.
  실제 실행 시 checkout SHA·dirty 상태와 측정 대상 패키지를 다시 고정한다.
- CLI `0.4.0`의 게시·새 설치 기능 검증은 [배포 기록](../../npm-release-0.4.0.md)에 있다.
  서버 SDK는 별도 배포물이므로 소스 후보를 게시된 라이브러리로 표시하지 않는다.
- 현재 문서에 확인된 API 부하의 RPS·p95·동시 사용자 기준선은 없다.
  기능 검사 통과는 처리량 또는 운영 수용량의 근거가 아니다.
- [기존 AI 읽기 실험](../../validation-ai-reading-2026-11-08.md)은 작은 표본의
  소스 후보 실험이다. 입력 토큰 감소와 비캐시 입력·출력 증가가 함께 관측됐으므로
  현 게시 버전의 비용·개발 시간 절감으로 확대하지 않는다.
- [SDK 안내 실험](../../adoption/2026-11-11-sdk-guidance.md)은 원본 SDK 연결이
  아닌 직접 구현·복사가 대부분이었다. 안내 경로 참조와 실제 SDK 재사용을 나눈다.

## 진행 순서와 공통 완료 조건

`PERF-01`을 먼저 완료한 뒤 `PERF-02`부터 `PERF-05`를 독립 실행하고,
`PERF-06`에서 결과를 취합한다. 각 과제의 상태는 미착수 → 실행 중 →
근거 검토 완료로 관리한다. 중단·환경 실패·누락도 결과에 남긴다.

| 과제 | 우선순위 | 나중에 남길 산출물 | 현재 상태 |
| --- | --- | --- | --- |
| PERF-01 환경·측정 프로토콜 고정 | P0 | 실행 manifest와 제한값 | 미착수 |
| PERF-02 인증·권한 API 부하 | P1 | 언어·프로필·시나리오별 기준선 | 미착수 |
| PERF-03 목록 규모·DB 비용 | P1 | 데이터 크기별 지연·자원·정확성 | 미착수 |
| PERF-04 실제 설치 패키지의 AI 개발 효과 | P1 | 통합 성공·재사용·시간·usage 비교 | 미착수 |
| PERF-05 CLI 실행·문맥 크기 | P2 | 프로세스 시간·출력 바이트 분포 | 미착수 |
| PERF-06 보고와 다음 개선 과제 선정 | P1 | 정제된 보고서와 근거 목록 | 미착수 |

SLO와 처리량 목표는 아직 미정이다. 첫 기준선은 목표 충족 판정 대신 재현성과
측정 완전성을 판정한다. 개선 실험 전에는 배포 자원 예산, 대상 기능, 지연·오류율
목표를 확정한다. 임의의 RPS 숫자를 통과 기준으로 만들지 않는다.

## PERF-01 — 환경과 프로토콜 고정

- [ ] OS·CPU·메모리, 전원 모드, 언어·런타임·빌드 모드, 의존성 잠금 파일,
  프로세스·worker·스레드 수, DB 버전·pool·인덱스·데이터 seed를 기록한다.
  Java JIT 준비 시간과 Rust debug/release 등을 명시하고 모든 스택에 동일한
  CPU·메모리 예산을 준다. 프레임워크와 해싱 설정 차이도 남긴다.
- [ ] 소스 SHA, npm 버전·tarball hash, SDK 버전·해석된 원본 경로를 고정한다.
  소스 실행과 registry 설치 실험을 구분한다. 실행 중 의존성·안내를 변경하지 않는다.
- [ ] 부하 도구는 기존 도구를 먼저 조사한 뒤 하나를 선택해 버전·스크립트를 고정한다.
  결과에는 주입 방식, 목표 요청률, 실제 시도율·완료율, 동시 연결 수를 함께 남긴다.
  고정 동시성 방식의 포화 결과를 고정 요청률 실험과 직접 합치지 않는다.
- [ ] 최초 API 프로토콜은 준비 10초·측정 30초·각 조건 3회로 시작한다.
  인증 해싱은 동시성 1/2/4, 읽기는 1/4/8/16부터 한 단계씩 올린다.
  이는 초기 설계값이며 호스트 예산을 넘으면 낮추고 변경 이유를 기록한다.
- [ ] 실행 전 수치로 자원 상한·요청 timeout·전체 시간·최대 진행 요청 수를 정한다.
  상한 초과, OOM·과도한 swap, 계약 위반 시 중단한다. 부하 발생기 CPU·메모리·
  event-loop 지연도 측정하고, 발생기가 먼저 포화된 실행은 서버 한계로 해석하지 않는다.
- [ ] 전용 loopback 앱·임시 데이터만 쓴다. DB는 도구가 소유한 임시 클러스터 또는
  명시적으로 분리된 테스트 DB만 사용한다. 기존 포트·DB·프로세스를 재사용하거나
  종료하지 않는다. fixture 정리 대상은 이번 실행이 만든 자원으로 제한한다.

완료 기준: 다른 사람이 같은 입력과 제한값으로 재실행할 manifest가 있고,
측정 대상·제외 범위·실패 처리·비교식이 결과를 보기 전에 고정돼 있다.

## PERF-02 — 인증·권한 API 부하

대상 계약은 [메모리 세션 v1](../../../features/auth/specification.md),
[PostgreSQL 세션 v2](../../../features/auth/postgres-session-v2.md)다.
v1을 네 언어에서 먼저 측정하고 v2는 별도 표로 측정한다. v3 계정·SMTP 흐름은
이번 기준선에서 제외한다. 직접 SDK 호출과 실제 HTTP 결과도 합치지 않는다.

| 시나리오 | 준비와 부하 | 반드시 확인할 결과 |
| --- | --- | --- |
| 정상 로그인 | 같은 해싱 설정·자격 증명으로 `POST /auth/login` | 성공 응답·쿠키·새 세션, 해싱 포함 지연 |
| 세션 읽기 | 측정 전 만든 독립 세션으로 `GET /auth/me` | 올바른 사용자, 세션 수에 따른 지연 |
| 로그아웃 | 요청마다 유효한 세션·CSRF 준비, `POST /auth/logout` | 204, 이전 쿠키 재사용 시 401 |
| 권한·소유권 확인 | core 소비 앱의 `GET /api/documents/{id}` | 허용·역할 거부·다른 tenant/owner 거부 |
| 잘못된 로그인·제한 | 전용 실행에서 실패 창을 채우고 재요청 | 계약의 429·Retry-After, 올바른 자격 증명도 제한 |

- [ ] 세션 생성·fixture 준비는 측정 구간 밖에서 수행하고 준비 비용은 별도 기록한다.
  로그인→읽기→로그아웃 전체 흐름은 별도 혼합 시나리오로 정의한다.
  준비·측정 중 세션 TTL 만료 여부와 공유 peer IP의 제한 영향을 기록한다.
- [ ] 기본 보호 동작을 유지한다. 429를 성공 처리량으로 세지 않고 예상 제한 응답,
  의도한 거부, 예상 밖 오류를 구분한다. 제한 임계값을 조정한 진단 실행은 별도 표시한다.
- [ ] 시도 수·정상 응답 수·검증된 성공 RPS, p50/p95/p99, timeout·연결 오류,
  응답 코드별 수, CPU·RSS 최대값, DB pool 대기·사용량을 기록한다.
  HTTP 지연은 연결 pool 대기를 포함한 요청 시작부터 본문 수신까지로 정의한다.
- [ ] timeout을 0ms로 넣거나 지연 분포에서 조용히 제외하지 않는다. 완료 응답의
  지연 분포와 timeout 수·상한을 같이 제시한다. p99는 완료 표본 1,000개 미만이면
  참고값으로만 표시하고 반복별 분포·범위를 함께 남긴다.
- [ ] 부하 전후 Origin·CSRF·쿠키·폐기 세션·기본 거부·tenant 격리와 오류 시
  정보 노출을 확인한다. 부하 중에도 별도 검증 요청을 표본 검사한다.

Java의 [PasswordHashes.java](../../../implementations/java-spring/src/main/java/dev/featurestandards/auth/PasswordHashes.java)는
현재 encode/matches를 `synchronized`로 직렬화한다. 로그인 포화 원인 후보로
큐 대기와 CPU·메모리를 관측하되 원인 확정 전에는 구현을 바꾸지 않는다.
고정된 Argon2 비용을 낮추거나 메모리 경계를 제거한 결과는 동등 비교에서 제외한다.
특히 v2 계약의 Argon2id 64 MiB·t=3·p=4를 보존한다. 모든 프로필의 기본값이
같다고 가정하지 말고 실제 설정을 기록한다.

완료 기준: 네 언어 v1의 다섯 시나리오와 별도 v2 결과에 설정·표본·자원·오류가
모두 연결돼 있다. 구현 부재·환경 제한은 건너뜀으로 명시한다. 정상 응답의
내용이 틀리거나 보안 계약이 깨지면 해당 실행은 수용 불가다.

## PERF-03 — 목록 규모와 DB 비용

- [ ] 네 언어의 `offset-list-v1`은 동일 seed·typed schema·가시성 비율로
  1/100/1,000/10,000행을 만든다. 필터 없음·일부 일치·0건, 정렬·동점 ID,
  첫 페이지·후반 offset을 각각 측정한다. materialized 계약의 10,000행을 넘기지 않는다.
- [ ] `limit=1/100`, 반환 바이트 수, 전체 처리 지연·CPU·RSS를 기록한다.
  선택·정렬·페이지 절단 구간을 계측할 경우 HTTP 전체 지연과 분리한다.
- [ ] 단순 속도와 함께 `items/total/nextOffset`, 정렬 안정성, 숨은 행이 total에
  포함되지 않는지, 다른 tenant의 행이 노출되지 않는지 독립 기대값으로 검사한다.
- [ ] DB 목록은 현재 지원되는 **Python 전용**
  [postgres-list-v1](../../../features/listing/postgres-list-v1.md)에서만 별도 실행한다.
  10,000/100,000행, offset 0/1,000/10,000, limit 100을 시작 조건으로 삼고
  인덱스·가시성 선택도·정렬 조합별 지연, DB CPU·I/O·pool 대기를 기록한다.
- [ ] COUNT와 항목 조회의 계획·실측 비용은 전용 fixture의 `EXPLAIN (ANALYZE, BUFFERS)`로
  확인한다. 적절한 인덱스 유무를 구분하고 조회 timeout을 고정한다.
  offset 상한과 nextOffset 종료 규칙을 유지한다. 요청 간 snapshot 보장은 주장하지 않는다.

완료 기준: 메모리와 DB 결과를 다른 표에 제시하고, 행 수 증가에 따른 비용과
정확성 검사를 함께 설명한다. Python DB 결과를 다른 언어의 DB 지원 근거로 쓰지 않는다.

## PERF-04 — 실제 설치 패키지의 AI 개발 효과

기존 [평가 도구](../../../evals/core/README.md),
[reading runner](../../../tools/core_reading_eval.py),
[guidance runner](../../../tools/core_guidance_eval.py)를 조사한다.
현재 runner가 실제 설치본과 SDK 연결을 검증할 수 있는지 먼저 확인하고 부족한
부분의 수정은 이후 구현 과제로 남긴다. 도구가 이미 지원한다고 가정하지 않는다.

- [ ] 게시된 CLI를 새 전용 디렉터리에 정확한 버전으로 설치하고 archive hash를
  기록한다. starter에 필요한 신뢰한 SDK checkout도 SHA로 고정한다. 두 의존성을
  모든 비교 조건에 동일하게 제공하고 네 언어에서 정상 빌드 가능한 fixture를 준비한다.
- [ ] 다음 세 프로토콜을 별도로 사전 등록한다. 같은 기능 요구·권한·목록 계약을
  주고 React·DB·SMTP처럼 이번에 비교하지 않는 기능을 섞지 않는다.

| 프로토콜 | 비교 조건 | 답하려는 질문 |
| --- | --- | --- |
| A: 읽기 안내 | manual / full context / compact context, 모두 SDK 통합을 요구 | 안내 방식이 성공·읽기 비용·시간에 미치는 영향 |
| B: 앱 생성 | 수동 SDK 통합 / 설치 CLI의 core starter, 동일한 전이 과제 | starter가 실제 앱 완성과 SDK 재사용에 미치는 영향 |
| C: 자율 선택 | 구현 수단을 지정하지 않고 동일하게 CLI·SDK를 제공 | 제공된 환경에서 자발적으로 선택·연결하는가 |

- [ ] A는 언어별 세 조건의 여섯 순열을 한 번씩 사용한다(4언어 × 6블록 × 3조건 =
  72세션). B는 언어별 AB/BA 순서 각 2회로 시작한다(4언어 × 4블록 × 2조건 =
  32세션). C는 언어별 3회(12세션) 관찰한다. 총 116세션은 **향후 탐색 실험
  설계안**이며 아직 호출하지 않았다. 실행 전 비용·시간 한도를 확정하고, 예산에 맞춰
  횟수를 바꾸면 결과를 보기 전에 수정한다. 이 표본 수가 통계적 검정력을 보장하지 않는다.
- [ ] 과제·prompt·모델 요청 ID·관측 모델 ID·설정·도구 버전·session timeout을
  고정한다. 매번 새 세션에서 직렬 실행하고 조건 순서를 회전한다. 모델 ID가
  제공되지 않으면 unknown, 원격 prompt cache·호스트 캐시는 통제 범위를 명시한다.
- [ ] 실행 전에 1차 지표를 독립 HTTP·권한·목록 통합 성공률로 고정한다.
  2차 지표는 원본 SDK의 런타임 연결률, 모델 작업 시간, 빌드·채점 포함 전체 시간,
  input/cached/uncached/output/total로 나눈다. 토큰과 시간은 같은 지표로 취급하지 않는다.
- [ ] SDK 연결은 import 문자열만 보지 않는다. 해석된 모듈·의존성 원본 경로와 hash,
  실제 product route에서의 호출, 원본 보존·복사 여부를 검사한다. 생성 앱을 수정해
  통과시킨 결과는 원본 결과를 대체하지 않는다. 읽기 trace도 모델 이해의 증명이 아니다.
- [ ] 실패·timeout을 포함한 전체 분모, 완전 usage 쌍, 양쪽 성공 쌍을 각각 보고한다.
  누락은 null로 두고 재시도는 별도 행으로 남긴다. 절감률은
  `(기준 합계 - 비교 합계) / 기준 합계`로 계산하고 음수도 보존한다.
  cached를 input에 다시 더하지 않는다. 비용은 사용 모델·단가·확인 날짜·캐시 과금이
  확인된 경우에만 산출하며, 미확인 비용·timeout 사용량은 추정 0으로 넣지 않는다.
- [ ] 프로토콜·언어별 표본과 짝지은 변화·반복 편차를 제시한다. 신뢰구간은
  반복 블록을 단위로 계산하고 작은 표본의 한계를 명시한다. 성공한 앱만 골라
  전체 절감률로 발표하지 않는다. A/B/C 및 과거 실험 수치를 합산하지 않는다.

완료 기준: 실제 설치본·SDK·요청·결과가 연결되고 성공률과 비용·시간을 함께
해석할 수 있다. C의 선택 비율은 제공된 실험 환경의 선택 관찰이며 외부 채택률이
아니다. 실제 사용자 채택은 별도의 동의 기반 설치·지속 사용 근거가 필요하다.

## PERF-05 — CLI 실행 시간과 문맥 크기

- [ ] 정확한 설치본의 `list`, 같은 선택의 full/compact `context`를 새 Node
  프로세스로 실행한다. 조건별 준비 3회·측정 30회, 명령 순서를 회전하고
  p50/p95·최소/최대·exit code·출력 크기를 기록한다.
- [ ] 프로세스 시작부터 종료까지의 시간과 첫 출력 지연을 구분한다. 새 프로세스도
  OS 파일 캐시가 따뜻할 수 있으므로 cold start라고 표현하지 않는다.
  최초 npm 설치·네트워크 비용은 별도 시나리오로 측정한다.
- [ ] 26개 선택 각각의 full/compact UTF-8 JSON 바이트와 문서 hash·유효 경로를
  확인한다. 설치 경로 길이를 기록한다. 바이트 감소를 모델 토큰·비용·속도 절감으로
  바꾸어 주장하지 않는다. 모델에 실제 전달한 문서 본문은 별도 집계한다.

완료 기준: 준비·측정 횟수, 캐시 조건, 출력 정확성과 분포를 재현할 수 있다.

## PERF-06 — 보고와 다음 작업 선정

- [ ] 향후 보고서는 `docs/performance-validation-YYYY-MM-DD.md`에 작성한다.
  원시 로그·생성 코드·trace·자격 증명은 private 실행 디렉터리에 보관하고 Git에
  넣지 않는다. 공개본은 정제된 집계·manifest·근거 hash만 포함한다.
- [ ] 각 실행에 run ID, source/package/model identity, protocol/scenario, seed,
  자원 제한·설정, 반복, attempted/completed/success/rejected/error/timeout,
  지연·처리량·자원 또는 usage, 독립 검사 결과, 누락·중단 사유를 연결한다.
- [ ] 높은 처리량이어도 계약 위반 실행은 개선 성공으로 채택하지 않는다.
  baseline 완료 후 제품 SLO·예산을 정하고 실제 병목에 맞춘 개선 과제만 제안한다.
  구현 변경은 이 문서 작성 범위에 포함되지 않으며, 이후 요청 시 별도로 진행한다.
